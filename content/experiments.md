## なぜ記録するのか

機械学習は「試して、比べて、また試す」の繰り返しです。1 日に何十通りも設定を変えます。

記録していないと、こうなります。

- 「先週 0.92 が出た設定、何だったっけ」
- 「今日の 0.89 は、昨日より良いのか悪いのか」
- 「この結果、どのデータで出したんだっけ」

**半年後どころか、翌週には分からなくなります。** モデルの精度を 1% 上げる工夫より、記録を残す習慣のほうが先に効きます。

## 何を記録するか

3 つに分けて残します。

| 種類 | 例 | なぜ要るか |
|---|---|---|
| **設定** | モデル、欠測の埋め方、分割数、シード | 再現するために要る |
| **結果** | 正解率、RMSE、交差検証の平均 | 比較するために要る |
| **文脈** | いつ、どのラボ、どのデータ、メモ | 後から意味を思い出すために要る |

各ラボの下部にある「この結果を記録する」から、これらがまとめて残ります。実験名を同じにしておけば、1 つの実験としてまとまります。

## 「そこまでの最良」の線を見る

「試行の推移」のグラフには 2 本の線があります。

- **実線** — 各試行のスコア。上下します
- **点線** — そこまでの最良。下がることはありません

**点線が平らになったら、いまの探索範囲では頭打ち**です。同じつまみを回し続けても伸びません。別の設定に手を付けるか、探索範囲そのものを広げる合図です。

これを見ずに闇雲に試行を重ねるのが、最もよくある時間の使い方の失敗です。

## どの設定が効いたのか

「どの設定が効いたか」タブは、設定ごとに「その値を変えたときスコアがどれだけ動いたか」を並べます。

- **上にある設定** — 結果への影響が大きい。ここを詰める価値がある
- **下にある設定** — いくら回しても結果が変わらない。触るだけ時間の無駄

限られた時間をどこに使うかの判断材料になります。

ただし注意が要ります。この表は**他の条件が揃っているかを確認していません**。「モデルを変えたときスコアが動いた」ように見えても、たまたまその試行だけ別のデータを使っていたのかもしれません。

「1 つの設定を詳しく見る」の箱ひげ図で、**箱同士が重なっていないか**を確かめてください。重なっているなら、その差は偶然の範囲かもしれません。交差検証のばらつきを見たとき（ラボ 8）と同じ考え方です。

## なぜ MLflow を使わなかったか

実験管理のツールとしては MLflow が業界標準です。このプロジェクトでは採りませんでした。理由は 2 つあります。

1. **本体は pandas を 2.x に下げてしまう** — このプロジェクトは pandas 3.x で動いており、全ラボがそれを前提にしています。1 つの機能のために中核ライブラリを下げるのは割に合いません
2. **軽量版（mlflow-skinny）でも 28 個の依存が付く** — fastapi、databricks-sdk、opentelemetry など、個人の学習用途では一度も使わないものが大半です

そしてこのプロジェクトは最初から「**サーバーを立てない・ローカルのファイルだけ**」を通してきました。MLflow の UI はサーバーです。

そこで、既にあるデータ基盤（Parquet + DuckDB）に乗せました。記録は `data/experiments/runs.parquet` の 1 ファイルだけです。中身が見えるぶん、実験管理が何をしているのかも分かりやすくなっています。

> **チームで使うなら MLflow を検討してください。** 複数人で結果を共有する、モデルそのものをバージョン管理する、といった用途では、ここで作ったものでは足りません。個人が手元で回す範囲なら、この形で十分です。

## 記録の実体

```
data/experiments/runs.parquet
```

1 ファイルです。CSV で書き出して他のツールへ持ち出すこともできます。取得データと同じく git 管理外なので、リポジトリは膨らみません。

列は `設定:` と `結果:` の接頭辞で分けてあります。ラボによって設定項目が違うので、新しい列が増えたら既存の行は空欄になります。これを許す作りにしてあるため、どのラボからでも同じ実験名に記録できます。

## 実務での次の一歩

このラボで扱っていないものを挙げておきます。

- **モデルそのものの保存** — 「一番良かった設定」だけでなく、学習済みのモデルを保存して後で読み込む
- **データのバージョン** — 同じ設定でもデータが変われば結果は変わります。データのハッシュを記録する方法があります
- **コードのバージョン** — git のコミットハッシュを一緒に記録すると、完全に再現できます

まずは**記録する習慣**からです。上の 3 つは、それが身についてから足せば十分です。

## この構成が現実のどこに対応するか

このカタログは小さな仕組みですが、実務のデータ基盤と同じ役割を持っています。

| ここでやっていること | 実務での呼び名 |
|---|---|
| API・RSS から取得して保存 | 取り込み（Ingestion / ELT） |
| Parquet で列指向に保存 | データレイク |
| DuckDB で SQL 集計 | 分析エンジン（BigQuery / Snowflake の位置） |
| 取得条件を JSON で残す | メタデータ管理・データリネージ |
| ラボから同じデータを参照 | 特徴量の一元管理（Feature Store） |

**規模が変わっても、層の分け方は同じ** です。ここで身につく段取りは、クラウドのデータ基盤にそのまま移ります。

## 5 つの取得元で何が学べるか

| 取得元 | 向く題材 | 相性の良いラボ |
|---|---|---|
| e-Stat（政府統計） | 人口・世帯・経済。**因果を考える練習** | 8 テーブルデータ |
| 気象庁 | 気温・降水。**外部要因として最強** | 9 時系列 |
| 株価・指数 | 予測できない系列の実例 | 9 時系列 |
| ニュース RSS | 日本語テキスト | 10 テキスト |
| オープンデータ | 地域比較、施設分布 | 8 テーブルデータ |

**気象データは、ほぼどんな予測にも効きます。** 小売の来客、電力需要、飲料の売上、事故件数 — 屋外の行動が関わるものは必ず天候の影響を受けます。手元のデータに外部データを 1 つ足すなら、まず気温です。

## 実務での使われ方

**外部データの接続が最も費用対効果が高い**

社内データだけで精度を詰めるより、外部データを 1 列足すほうが効くことがよくあります。気温、祝日、近隣イベント、地域の人口構成。**「特徴量を作る」前に「データを増やす」** のが順序です。

**取得条件を残さないと再現できない**

「2 年前の分析をやり直したい」という依頼は必ず来ます。API のパラメータ、取得日時、行数を残しておかないと、同じ表は二度と作れません。**API 側のデータが遡って修正されることもある** ので、取得時点のスナップショットを保存しておく意味があります。

**Parquet と DuckDB を選ぶ理由**

- 列指向なので、**必要な列だけ読む**（数十列のうち 3 列なら読み込み量も 3 列分）。
- 型が保存されるので、CSV のような「日付が文字列になる」事故が起きない。
- 圧縮が効き、CSV の 1/5〜1/10 になる。
- DuckDB はサーバ不要で、ファイルを直接 SQL で読める。**数百万行までなら、これで十分速い。**

数千万行を超え、複数人で共有する段階になって初めて、BigQuery や Snowflake のようなクラウド DWH が必要になります。**最初からそこへ行く必要はありません。**

## データを扱うときの注意

- **利用規約とライセンスを確認する。** 出典表示が必要なもの、再配布が禁止されているものがあります。
- **アクセス頻度を抑える。** 公開 API に短い間隔で叩き続けるのは迷惑行為です。取得したらローカルに保存し、以後はそれを使います。
- **個人情報を取り込まない。** 分析に不要な識別子は、取り込みの時点で落とします。
- **git に入れない。** データはリポジトリを膨張させ、履歴から消しにくくなります。`data/` は管理外にしてあります。

## このカタログで試してほしいこと

1. 気象データを取得し、時系列ラボで **気温を特徴量に足したときの誤差の変化** を見る。外部データの効き目が数字で分かります。
2. ニュース RSS を複数フィード取得し、テキストラボでトピックを比べる。**媒体によって語彙が違う** ことが、そのままトピックの差になって出ます。
3. SQL の例を書き換えて集計してみる。前処理を Python で回すより、SQL で済ませたほうが速い場面が多いことが分かります。
